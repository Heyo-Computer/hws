Auth, tokens & the admin API

Two separate doors: a per-deployment sign-in gate on the data plane, and a two-tier gate on the admin API. App-tokens open both, each within their scope.

The sign-in gate

Any deployment can put a gate in front of everything it serves. It runs in the proxy, before a backend is chosen, so the application behind it needs to know nothing about it:

"auth": {
  "provider": ["google", "app-token"],
  "client_id": "…apps.googleusercontent.com",
  "client_secret": { "secret": "google", "key": "client_secret" },
  "allowed_domains": ["example.com"],
  "public_paths": ["/healthz", "/api/webhook"],
  "forward_identity": true
}
  • Providers are alternatives. google admits a person with a session (domain matching uses Google's hd claim, so a personal Gmail with a lookalike address does not pass); app-token admits a program presenting Authorization: Bearer applb_…; jwt admits a token another service issued. A gate listing several admits any of them. The default is Google-only — a gate that should accept programs must say "app-token" or "jwt" explicitly.
  • public_paths are prefix-matched and skip the gate entirely — health checks and webhooks.
  • forward_identity adds x-auth-request-email/-user upstream for signed-in people, and app-lb strips those header names from inbound requests so nobody can forge them. A token is not a person: token-admitted requests carry no identity headers.

Verifying a JWT

The jwt provider verifies a token somebody else issued, and keeps nothing: no session, no token table. For an application whose users already sign in elsewhere — and so that app-lb never becomes a second place identity lives.

"auth": {
  "provider": "jwt",
  "jwt": {
    "secret":        { "secret": "heyo-auth", "key": "jwt_secret" },
    "algorithms":    ["HS256"],
    "issuer":        "auth-service",
    "audience":      "heyo-app",
    "subject_claim": "userId",
    "require":       { "role": ["user", "admin"] }
  }
}
  • algorithms is required and has no default. A token names its own algorithm in a header the caller controls; a verifier that trusted it would accept both an unsigned token (alg: none) and one signed HS256 with the gate's public key as the secret. The spec decides, never the token — and a block naming an algorithm its key could not verify is refused at registration.
  • The key is one of secret (a secret-store reference, for HS*), public_key (an inline PEM) or jwks_url (the issuer's key set, cached and refetched on an unknown kid).
  • require is the allow-list — any claim, against a value or a set. allowed_domains/allowed_emails describe a Google identity and are refused on a gate with no google provider, rather than appearing to restrict something they do not.
  • A token with no exp is refused. app-lb did not issue it and could not revoke it, so its expiry is the only thing that ever stops it.
  • The identity goes upstream from subject_claim, email_claim and name_claim. Nothing else is copied: the token is still in the Authorization header for the application to read itself.
The gate runs before the cold-start wait. An unauthenticated request never boots a VM. An API client hitting a Google-only gate gets an immediate 401 {"error":"authentication required"} from app-lb itself — the request never reaches the deployment and never wakes it. If a scale-from-zero deployment is "not waking up" for programmatic callers, check the gate's provider list and public_paths first.

App-tokens

The credential a program carries. Minted through the admin API (or heyctl token mint), scoped, optionally expiring, revocable instantly. The shape is applb_<id>_<secret> — greppable on purpose, and only the secret's SHA-256 is stored, so the token file is not a fleet compromise and there is no "reveal" endpoint.

Scope axisValuesGoverns
adminnone / view / admin What the token may do on the admin API. none still passes data-plane gates — the shape for a token handed to an application.
deploymentsids, or ["*"] Which deployments it may touch — both the per-deployment admin routes (exec, shell, scale, delete) and data-plane gates.
namespaceone namespace A wall around everything: see Namespaces.
# a token for CI to reach one deployment's data plane, expiring in a week
heyctl token mint ci-secrets -d secret-service --expires-in 168 -q

# a fleet-wide operator token
heyctl token mint ops --admin admin --all-deployments

heyctl token set re-scopes a token without changing its secret; heyctl token revoke takes effect on the next request.

Federated bearers

With APP_LB_AUTH_URL set, the admin API accepts a third credential: a bearer the Heyo auth service issued. app-lb never sees the user's password and mints them nothing — it asks GET /api/auth/scopes what the bearer may reach and enforces the answer with the same namespace wall a namespace token gets. Precedence is Basic, then a local applb_ token, then the auth service; a local token is never sent upstream. Answers are cached by the bearer's hash, refusals briefly, and an unreachable auth service fails closed.

The admin API's two tiers

Unset, the admin listener is open (it binds loopback). Setting APP_LB_DASHBOARD_PASSWORD gates the view tier — the directory, /metrics, the dashboard, /security, /feeds. Setting APP_LB_ADMIN_AUTH=1 extends the gate to the CRUD tier — everything that changes state or reads specs.

Scoped tokens are narrowed rather than refused where that makes sense: a token scoped to one deployment sees a directory, /metrics and /security filtered to that deployment, and is refused fleet-wide routes (creating deployments, reading secrets, minting tokens) outright — a token cannot widen itself.

Block rules and detection

Operators can arm block rules (by client IP, host, path, method, user-agent) that the proxy enforces with an anonymous 403 — the refusal deliberately does not say which property matched. A built-in analyzer (on unless APP_LB_SIEM=0) watches access and auth failures, folds repeats, and raises findings on GET /security with suggested rules.

It also recognises automated clients — AI agents (ChatGPT-User, Claude-User), AI labs' crawlers (GPTBot, ClaudeBot, CCBot), search engines, scripts and scanners — from the User-Agent, and checks each claim against the IP ranges the operator publishes: verified, spoofed, claimed (ranges not loaded) or unverifiable (none published). GET /security carries the per-deployment table as bots, filterable with ?class=, and each row offers a ready rule that blocks that agent on that deployment. A spoofed claim raises bot.spoofed. A User-Agent is self-asserted; Web Bot Auth signatures are not verified yet.
